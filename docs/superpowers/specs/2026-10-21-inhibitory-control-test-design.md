# 발달장애학생 억제적 통제 검사 웹사이트 — 설계 문서

작성일: 2026-10-21

---

## 1. 의도와 배경

중·고등학교 발달장애학생의 **억제적 통제(inhibitory control)** 를 브라우저에서 재는 검사 도구를 만든다. 결과는 교사와 작업치료사가 해당 학생의 집행기능 지도·치료 자료로 쓴다.

**풀려는 문제는 측정 신뢰도다.** 기존 고/노고(Go/No-Go) 검사는 흥미 요소가 없어서 발달장애학생이 과제에 붙어 있지 못한다. 그래서 나온 반응시간과 오류율이 그 학생의 실제 억제 능력이 아니라 "집중하지 않은 상태"를 재게 되고, 정반응·억제 반응을 제대로 끌어내지 못해 결과를 쓸 수가 없다. 이 도구의 존재 이유는 **학생이 과제를 끝까지 수행하게 만들어, 나온 숫자가 실제 억제 능력을 가리키게 하는 것**이다.

흥미 요소를 하나로 고정할 수는 없다. 학생마다 좋아하는 것이 아주 다르고(어떤 학생은 영상, 어떤 학생은 노래), 한 가지로 정하면 그 학생에게만 통한다. 따라서 흥미 요소는 **교체 가능한 테마**로 두고, 과제 구조와 측정 방식은 테마와 무관하게 동일하게 유지한다.

## 2. 목표 / 비목표 / 안티목표

### 목표

1. 표준 고/노고 구조를 유지한 채, 발달장애학생이 **끝까지 수행**하게 만든다.
2. 교사·작업치료사가 결과 화면을 보고 **지도 방향을 바로 정할 수 있게** 한다(억제력 문제인지, 주의력 문제인지, 지속 시간 문제인지 구분).
3. 학생이 **혼자서** 켜서 끝낼 수 있게 한다. 글을 읽을 수 없어도 가능해야 한다.
4. 수준 차이가 **매우 큰** 집단을 한 도구로 커버한다.
5. PC와 모바일 브라우저 양쪽에서 동작한다.
6. 결과가 **해석 가능한 상태인지 아닌지**를 도구가 스스로 알려준다.

### 비목표 (이번 범위에 넣지 않는다)

- 서버, 계정, 로그인, 기기 간 동기화
- 교사가 직접 영상·음원·이미지를 업로드하는 기능
- 규준(norm) 기반 표준점수, 백분위, 진단적 판정
- 억제적 통제 이외의 집행기능 영역(작업기억, 인지적 유연성) 측정
- 인쇄용 레이아웃 전용 설계
- 다국어

### 안티목표 (이게 생기면 기술적으로 작동해도 실패다)

- **게임성이 측정을 흔드는 것.** 보상·연출이 과해서 반응시간이 흥미 요소에 의해 오염되면 실패다. 과제 흐름을 끊는 보상(중간 영상 재생 등)을 넣지 않기로 한 이유가 이것이다.
- **글 읽기를 요구하는 것.** 학생이 보는 화면에 읽어야 이해되는 문장이 있으면 실패다.
- **오반응에 부정적 피드백을 주는 것.** 발달장애학생에게 실패 신호는 과제 이탈을 부른다.
- **난이도가 다른 회차의 숫자를 나란히 보여주는 것.** "좋아진 것"과 "쉬운 단계로 내려간 것"이 구별되지 않으면 자료로서 해롭다.
- **결과가 진단처럼 보이는 것.** 이 도구는 지도 자료를 만들 뿐이다.

## 3. 사용자와 사용 맥락

| | |
|---|---|
| **검사받는 사람** | 중·고등 발달장애학생. 수준 차이를 **최대로** 상정한다. 글을 못 읽는 학생부터 글을 읽는 학생까지. |
| **검사를 진행하는 사람** | 원칙적으로 학생 본인(독립 실행 우선). 불가능한 경우 교사·치료사의 **최소한의** 지원. |
| **결과를 보는 사람** | 교사, 작업치료사 |
| **장소** | 학교 교실, 치료실, 일상 상황 |
| **기기** | **스마트폰 중심.** 웹 주소로 접속한다. |
| **1회 소요** | 1분 ~ 5분 (학생이 집중을 유지할 수 있는 현실적 범위) |

**스마트폰이 주 기기다.** PC·태블릿에서도 동작하게 만들되, 레이아웃과 반응 영역은 **세로 모드 스마트폰을 기준으로 설계한다.** 교사가 결과를 보는 화면도 작은 화면에서 먼저 읽히게 만든다.

**"독립 실행 우선"의 의미:** 교사·치료사의 개입은 ① 처음 설정(학생 선택, 테마 선택, 길이 선택)과 ② 끝난 뒤 결과 확인, 두 군데로 제한한다. 그 사이에는 학생 혼자 화면만 보고 끝까지 간다.

설정 화면에는 글이 있으므로 학생 혼자 통과할 수 없다. 따라서 **운용은 "교사가 설정하고 시작을 누른 뒤 자리를 비운다"** 이고, 목표 3은 정확히 말하면 **"검사가 시작된 뒤부터 끝까지 학생 혼자"** 를 뜻한다. 사용자가 말한 "불가능하다면 최소한의 지원"이 이 지점이다.

그 최소한의 지원을 한 번의 탭으로 줄이기 위해, 시작 화면에 **"지난 설정으로 바로 시작"** 버튼을 둔다 (내 판단). 같은 학생을 반복 검사할 때 교사는 이 버튼 하나만 누르면 된다. 연습이 끝난 뒤의 난이도 추천 화면도 추천값이 선택된 상태로 **8초 뒤 자동 진행**한다 (내 판단) — 교사가 자리에 없어도 검사가 멈추지 않는다.

## 4. 제약

- **웹 주소로 접속한다.** 한 번 열어본 뒤에는 인터넷이 끊겨도 동작해야 한다(오프라인 캐시).
- **연구·논문·과제 산출물로도 쓰인다.** 따라서 ① §5.8의 판정 기준값에 문헌 근거가 필요하고, ② 문항 단위 원자료를 분석 도구로 내보내는 형식이 중요하며, ③ 측정 조건(기기, 브라우저, 도구 버전)이 결과와 함께 기록되어야 한다.
- **결과는 검사한 기기에만 저장한다.** 개인정보가 기기 밖으로 나가지 않는다. 대신 브라우저 데이터를 지우면 결과가 사라지므로, 결과를 파일로 내보내 보관하는 수단이 반드시 있어야 한다.
- **반응시간을 밀리초 단위로 신뢰할 수 있어야 한다.** 측정 도구이므로 입력 지연, 애니메이션 지연이 반응시간에 섞여서는 안 된다.
- **학생 화면에 문장이 없어야 한다.**
- **터치와 마우스 양쪽에서 같은 반응시간 특성을 가져야 한다.**

## 5. 결정된 설계

아래는 브레인스토밍에서 합의된 내용이다. "(내 판단)" 표시가 있는 항목은 사용자가 명시하지 않아 설계자가 정한 것이다.

### 5.1 과제 구조 — 고/노고

표준 고/노고를 유지한다.

- 화면 가운데에 그림 하나가 제시된다.
- **Go 문항**: 정해진 그림이 나오면 누른다.
- **No-Go 문항**: 다른 그림이 나오면 누르지 않고 참는다.
- 반응 입력은 **화면 전체 또는 화면 하단의 큰 버튼 하나**. 입력 수단은 하나뿐이다(선택지 없음).
- 문항은 자동으로 넘어간다. 학생이 다음으로 넘기는 조작은 없다.

**문항 순서 (내 판단)**: 규칙은 다음 세 가지다.

1. No-Go 문항은 연달아 나오지 않는다.
2. No-Go 사이의 Go 개수를 **1~4개 사이에서 무작위**로 둔다.
3. No-Go 비율(§5.2)은 **세션 전체의 평균 비율**이다. 고정 윈도가 아니다.

규칙 2가 중요하다. "No-Go 직전에 Go가 반드시 2개 이상"으로 두면, 3단계의 33% 비율과 동시에 만족시킬 수 있는 배열이 `Go Go 참기`의 무한 반복 하나뿐이 된다. 그러면 학생이 **세 번째 박자에 안 누르는 리듬을 학습**해버려서, 억제가 아니라 리듬 기억을 재게 된다 — 고/노고가 억제를 재는 원리 자체가 무너진다. 간격을 흔들어야 "누르는 습관"이 형성된 상태에서 예측 불가능하게 억제를 요구할 수 있다.

같은 이유로 세션 시작 직후 첫 3문항은 Go로 고정한다 (내 판단). 습관이 형성되기 전의 No-Go는 억제를 재지 못한다.

### 5.2 난이도 3단계

단계가 바뀌어도 **과제 구조는 바뀌지 않는다.** 바뀌는 값은 네 가지뿐이다.

| | 1단계 (쉬움) | 2단계 (보통) | 3단계 (어려움) |
|---|---|---|---|
| 그림이 화면에 머무는 시간 | 4.0초 | 2.4초 | 1.4초 |
| 문항 사이 간격 (내 판단) | 1.5초 | 1.2초 | 0.9초 |
| No-Go 문항 비율 | 5문항 중 1개 (20%) | 4문항 중 1개 (25%) | 3문항 중 1개 (33%) |
| Go 그림 ↔ No-Go 그림 차이 | 범주가 완전히 다름 (강아지 vs 자동차) | 같음 (범주가 완전히 다름) | 같은 범주 안 다른 종류 (강아지 vs 고양이) |

**모든 단계에서 두 그림의 차이를 확실하게 벌린다.** 3단계라도 "앉은 강아지 vs 뛰는 강아지" 수준의 미세한 차이는 쓰지 않는다 — 발달장애학생에게는 난이도 상에서도 그 정도는 적절하지 않다. 가장 어려운 단계의 변별 수준이 **강아지/고양이**다.

지각 변별 난이도는 3단계에서만 올린다. 1단계와 2단계는 같은 그림 쌍을 쓰고 **시간과 비율로만** 차이를 둔다.

**반응 허용 구간 (내 판단)**: 그림이 보이는 동안 + 그림이 사라진 뒤 0.5초. 그 뒤의 입력은 무시하고 "무반응"으로 처리한다.

**반응하면 그림이 바로 사라진다 (내 판단).** 학생이 누르는 순간 자극을 치우고 곧바로 문항 사이 간격으로 넘어간다. 표의 시간은 **최대 제시 시간**이다.

이유: 고정 진행이면 1단계에서 0.5초에 반응한 학생이 남은 3.5초를 멍하니 기다리게 된다. 그 빈 시간이 주의 이탈과 조급 반응을 스스로 만들어낸다 — 이 도구가 풀려는 바로 그 문제다. 또 반응으로 문항이 끝나므로 같은 시간에 문항이 더 많이 들어가고, 그 덕분에 §5.6의 No-Go 문항 수 부족 문제가 상당 부분 해소된다.

**단, 세션은 시간이 아니라 문항 수로 끝난다 (내 판단).** 학생이 빠르면 선택한 길이보다 짧게, 느리면 길게 걸린다. 측정 도구에서는 회차마다 문항 수가 달라지는 것이 시간이 달라지는 것보다 훨씬 나쁘기 때문이다. 결과에는 **실제 소요 시간**을 기록한다. 교사는 언제든 중단할 수 있다(§5.10).

### 5.3 연습 블록과 난이도 추천

본 검사 전에 **연습 8문항**을 돌린다(내 판단: Go 5 / No-Go 3).

- 규칙은 **소리와 움직임으로만** 전달한다. 글은 쓰지 않는다. 그림이 나오고 버튼이 스스로 눌리는 시범, 정답 시 짧은 소리와 칸 채워지는 애니메이션, No-Go 시 그림이 흔들리며 버튼이 흐려지는 연출.
- **연습은 2단계 타이밍으로 돌린다** (내 판단: 제시 2.4초, 간격 1.2초). 중간값이라 위로도 아래로도 추천이 가능하다. 1단계 속도로 연습시키면 거의 모두 통과해서 추천이 무의미해지고, 3단계 속도면 거의 모두 탈락한다.
- No-Go 3문항으로는 억제 능력을 통계적으로 판별할 수 없다. 연습의 목적은 **능력 측정이 아니라 "규칙을 이해했는가"** 의 확인이다.

**추천 규칙 (내 판단 — 파일럿 후 조정 대상)**

| 연습 결과 | 추천 |
|---|---|
| Go 5/5 정반응 + 참기 3/3 성공 + 평균 반응 1.0초 미만 | 3단계 |
| Go 3개 이상 정반응 + 참기 1개 이상 성공 | 2단계 |
| 위에 못 미침 | 1단계 |
| 재시도 후에도 Go 정반응 1개 이하 | 검사 중단 안내 |

- 조건에 못 미치면 **연습을 1회 재시도**한다. 재시도는 한 번만.
- **최종 결정은 교사가 한다.** 추천값이 선택된 상태로 표시되고, 8초 뒤 자동으로 그 값으로 진행한다(§3).
- "지금은 검사가 어렵습니다" 안내는 학생 화면이 아니라 **교사 화면**에 뜬다. 학생에게 실패를 알리지 않는다.
- 연습 결과는 본 검사 지표에 **포함하지 않는다.** 단 추천 근거로 원자료에 함께 저장한다.

### 5.4 흥미 요소 — 수집형

**정반응마다 아이템이 하나씩 모여 그림이 완성되는** 구조. 브레인스토밍에서 세 가지 안(수집형 / 중간 보상 재생 / 단계 통과형) 중 사용자가 수집형을 선택했다.

- 화면 아래에 빈 칸 격자가 있다. 정반응마다 칸 하나가 채워진다.
- **참기 성공(No-Go 정반응)도 칸을 채운다.** 억제에 보상이 가야 억제가 강화된다.
- **오반응에는 아무 일도 일어나지 않는다.** 칸이 채워지지 않을 뿐, 소리나 표시로 실패를 알리지 않는다.
- **격자 칸 수는 전체 문항 수의 70%로 잡는다** (내 판단). 전체 문항 수와 같게 두면 한 번이라도 틀린 학생은 격자를 끝까지 채울 수 없다.
- **종료 애니메이션은 항상 재생한다** (내 판단). 격자가 덜 찼으면 부분 채움 상태로 남기고, 그래도 애니메이션은 나온다. 보상이 안 나오는 것 자체가 실패 신호이고, 그건 §2의 "오반응에 부정적 피드백을 주지 않는다"를 위반한다. 애니메이션은 성취의 대가가 아니라 **끝까지 한 것에 대한 마무리**다.
- 조급 반응(§5.7)으로 맞춘 Go 문항은 칸을 채우지 않는다. 보상이 "그냥 누르기"를 강화하면 안 된다. 다만 이때도 실패를 알리는 표시는 없다.
- **과제 흐름을 끊지 않는다.** 보상 때문에 검사가 멈추는 구간이 없다. 중간 영상·노래 재생을 택하지 않은 이유가 이것이다.
- 채워지는 연출은 **짧고 작게** (내 판단: 300ms 이내, 화면 가운데를 가리지 않음). 다음 문항의 반응시간에 영향을 주면 안 된다.

### 5.5 테마

테마는 **교사가 학생별로 바꿔 끼운다.** 어떤 테마를 골라도 같은 지표가 같은 방식으로 나온다.

**프리셋 6종 (내 판단)**: 동물, 탈것, 음식, 과일, 도형, 날씨. 각 테마는 ① Go 그림, ② 다른 범주의 No-Go 그림(1·2단계용), ③ 같은 범주의 No-Go 그림(3단계용), ④ 모으는 아이템, ⑤ 완성 애니메이션을 제공한다.

예 — 동물 테마: Go=강아지, 1·2단계 No-Go=자동차, 3단계 No-Go=고양이, 아이템=뼈.

**그림은 코드에 내장한 SVG 또는 이모지로 만든다 (내 판단).** 외부 이미지 파일에 의존하지 않아 인터넷 없이 동작하고, 저작권 문제가 없고, 어느 화면 크기에서도 깨지지 않는다.

교사 업로드는 비목표다(§2).

### 5.6 세션 길이

교사가 **짧게 / 보통 / 길게**를 고른다. 기본값은 보통.

| | 목표 시간 |
|---|---|
| 짧게 | 약 1분 |
| 보통 | 약 3분 (기본값) |
| 길게 | 약 5분 |

세션은 시간이 아니라 **문항 수로 끝난다**(§5.2). 길이 선택은 실질적으로 문항 수 선택이고, 분 단위 표기는 목표치다.

**문항 수 테이블 (내 판단 — 파일럿 후 조정 대상)**

문항 길이는 `평균 반응시간 + 문항 사이 간격`(Go)과 `최대 제시 시간 + 문항 사이 간격`(No-Go)의 가중 평균으로 추정했다. 가정한 평균 반응시간은 1단계 1.5초, 2단계 1.2초, 3단계 1.0초다.

| | 짧게 (약 1분) | 보통 (약 3분) | 길게 (약 5분) |
|---|---|---|---|
| 1단계 | 18문항 (No-Go 약 4) | 50문항 (약 10) | 85문항 (약 17) |
| 2단계 | 22문항 (No-Go 약 6) | 65문항 (약 16) | 100문항 (약 25) |
| 3단계 | 30문항 (No-Go 약 10) | 85문항 (약 28) | 100문항 (약 33) |

**문항 수는 100개에서 끊는다** (내 판단). 그보다 길면 피로가 억제 능력보다 큰 변수가 되어 측정이 오염된다. 2·3단계 '길게'가 이 상한에 걸린다.

**남은 제약 (내 판단):** 억제 지표는 No-Go 문항 수가 적으면 해석할 수 없다. 위 표에서 **1단계·짧게(약 4개)와 2단계·짧게(약 6개)** 가 §5.8의 기준(8개)에 미달한다. 두 조합은 결과 화면에서 "억제 지표는 참고용"으로 표시하고, 설정 화면에서 미리 경고한다.

**비율을 임의로 올려 보정하지 않는다.** 그러면 회차 간 비교가 깨진다. 짧은 세션은 억제 지표를 내기 위한 것이 아니라 **과제에 적응시키고 참여도를 확인하기 위한 것**으로 쓴다 — 결과 화면에도 그렇게 적는다.

§5.2의 "반응하면 그림이 바로 사라진다" 결정이 여기서 효과를 낸다. 고정 진행이었다면 1단계 보통이 33문항(No-Go 약 7개)으로 기준에 미달했을 것이다.

### 5.7 결과 화면과 지표

사용자가 요구한 지표는 정반응/오반응 횟수와 반응 속도다. 거기에 설계자가 네 가지를 더했고, 사용자가 전체를 승인했다.

**상단 요약 타일**

1. **억제 실패** — 참아야 할 때 누른 횟수 / No-Go 문항 수. **억제적 통제의 핵심 지표.** 가장 눈에 띄게 둔다.
2. **정반응** — 눌러야 할 때 누른 횟수 / Go 문항 수
3. **누락** — 눌러야 할 때 안 누른 횟수. 억제가 아니라 **주의력** 문제다.
4. **평균 반응속도** — 정반응 문항만 계산
5. **반응 일관성** — 반응시간 표준편차. 평균이 같아도 300ms·900ms를 오가는 학생과 꾸준히 600ms인 학생은 완전히 다르다. 편차가 크면 주의가 계속 끊기고 있다는 신호다.
6. **조급 반응** — 0.2초 안에 누른 횟수. 자극을 보고 판단한 게 아니라 그냥 누른 것이다. 신뢰도 문제를 직접 잡아내는 칸이다.

**지표 정의 (내 판단 — 구현과 테스트가 이 정의를 따른다)**

| 지표 | 정의 |
|---|---|
| 조급 반응 | 자극 제시 후 **200ms 미만**의 입력. Go·No-Go 양쪽 문항에서 센다. 분모는 전체 문항(Go+No-Go). |
| 정반응 | Go 문항에서 **200ms 이상** 허용 구간 안의 첫 입력. 정확히 200ms는 정반응이다 — 고/노고 문헌의 통상 관례가 `RT < 200ms`를 조급 반응으로 보는 것이다. |
| 누락 | Go 문항에서 허용 구간 안에 입력 없음 |
| 억제 실패 | No-Go 문항에서 허용 구간 안에 입력 있음 (200ms 이내 포함) |
| 참기 성공 | No-Go 문항에서 입력 없음 |
| 평균 반응속도 / 반응 일관성 | **Go 정반응 문항만.** 조급 반응은 제외 |

중복 계상 규칙:

- **Go 문항에서 200ms 이내에 누른 것은 정반응으로 세지 않는다.** 조급 반응으로만 센다. 평균 반응속도와 반응 일관성 계산에서도 빼고, 수집 칸도 채우지 않는다(§5.4). 자극을 보고 판단한 반응이 아니기 때문이다.
- **No-Go 문항에서 200ms 이내에 누른 것은 "억제 실패"와 "조급 반응" 양쪽에 각각 1로 센다.** 서로 다른 차원이므로 이게 맞다. 두 칸의 합이 문항 수를 넘을 수 있고, 화면에 그 점을 한 줄로 밝힌다.
- 한 문항에서 두 번 이상 누르면 **첫 입력만** 기록하고 나머지는 무시한다. 다만 연타 횟수는 원자료에 남긴다 — 충동성의 단서가 될 수 있다.
- 화면이 가려져 무효 처리된 문항(§5.9)은 모든 지표 계산에서 제외한다.

**오반응을 두 종류로 쪼개는 것이 이 화면의 핵심이다.** "억제 실패"와 "누락"을 합쳐 "오반응 5회"로 적으면 지도 방향이 반대로 간다.

**문항별 흐름 막대.** 문항을 가로로 늘어놓고 막대 높이로 반응시간을 보여준다. Go 정반응 / No-Go 정반응 / 억제 실패 / 누락을 색으로 구분한다. 언제 무너졌는지 한눈에 보인다.

**전반 vs 후반.** 앞 절반과 뒤 절반의 억제 실패 횟수와 평균 반응속도를 나란히 둔다. 발달장애학생에게는 "억제를 할 수 있나"보다 "얼마나 버티나"가 더 자주 문제다. 뒤로 갈수록 무너지는 패턴이 보이면 "회기를 짧게 끊어 반복"이라는 처방이 바로 나온다.

**회차별 추이.** 억제 성공률의 회차별 변화. **같은 난이도 단계끼리만** 그린다.

**해석 한 줄.** 위 수치에서 자동으로 뽑은 문장 한두 개(예: "실패가 후반에 몰려 있고 후반 반응속도도 느려졌습니다 — 억제 자체보다 지속 시간이 약한 쪽으로 보입니다"). **진단이 아니라 수치를 말로 바꾼 것**임이 분명해야 한다.

구현 방식 (내 판단): **문장과 발화 조건을 하나의 규칙 테이블로 분리**한다. 코드 안에 문장을 흩어놓지 않는다. 설계자가 초안 문장 세트를 작성하되, 이 산출물은 교사·치료사의 처방 결정에 직접 쓰이므로 **작업치료 전문가의 검토를 거친 뒤 확정**한다. 검토에서 문장이 바뀌어도 테이블 값만 교체하면 되는 구조로 둔다.

초안 규칙 (조건 → 문장의 방향):

| 조건 | 문장이 가리킬 방향 |
|---|---|
| 억제 실패가 후반에 몰리고 후반 반응속도가 느려짐 | 억제보다 지속 시간 — 회기를 짧게 끊어 반복 |
| 억제 실패는 적고 누락이 많음 | 억제보다 주의력 |
| 억제 실패가 전·후반에 고르게 많음 | 억제 자체의 어려움 |
| 반응 일관성 편차가 큼 | 주의가 계속 끊김 |
| 조급 반응이 많음 | 자극을 보기 전에 누르는 패턴 — 과제 이해 재확인 필요 |
| 전 구간 안정적이고 억제 실패 적음 | 현재 단계가 쉬울 수 있음 — 다음 회차 단계 상향 검토 |

**머리글에 항상 함께 적는 것**: 학생, 회차, 날짜, 테마, **난이도 단계**, 소요 시간, 문항 수.

### 5.8 검사 집중도 배지

결과 화면 맨 위에 **이 결과를 해석해도 되는지**를 알려주는 배지를 둔다. 이 도구가 풀려는 신뢰도 문제를 직접 다루는 장치다.

판정 규칙 (내 판단, 구현 중 조정 가능):

| 조건 | 표시 |
|---|---|
| 조급 반응이 **전체 문항(Go+No-Go)** 의 20% 이상 | **해석 주의** — 보고 누른 반응이 아님 |
| 누락이 Go 문항의 40% 이상 | **해석 불가** — 과제에 참여하지 않음 |
| **Go 누락이 5문항 연속** | **해석 주의** — 중간에 이탈한 구간 있음 |
| No-Go 문항 8개 미만 | **억제 지표 참고용** — 문항이 부족함 |
| 화면 가려짐으로 무효 처리된 문항이 10% 이상 | **해석 주의** — 검사가 자주 끊김 |
| 위 어느 것도 아님 | **양호 — 결과 해석 가능** |

"Go 누락 5연속"으로 둔 이유: "무반응 5연속"으로 두면 No-Go 참기 성공이 섞여서, **3단계에서 잘 참은 학생이 '해석 주의'로 찍힌다.** 이탈을 잡아내려는 조건이 정상 수행을 처벌하면 안 된다.

**위 숫자(200ms, 20%, 40%, 5연속, 8개, 10%)는 전부 임시값이다.** 문헌 근거로 확정한 값이 아니므로, 코드 한 곳의 설정 상수로 모아 두고 파일럿 결과와 전문가 검토로 조정한다.

### 5.9 데이터 저장과 내보내기

- **검사한 기기의 브라우저에만 저장한다** (localStorage). 서버 없음, 전송 없음.
- 저장 단위: 학생 → 회차 목록. 회차마다 설정값(테마, 난이도, 길이)과 **문항 단위 원자료**(문항 종류, 반응 여부, 반응시간)를 모두 남긴다. 지표는 원자료에서 계산한다 — 나중에 지표를 바꿔도 과거 회차를 다시 계산할 수 있다.
- **학생 식별은 교사가 입력한 이름 또는 별칭.** 그 이상의 개인정보는 받지 않는다 (내 판단).
- **내보내기 버튼이 반드시 있다.** 브라우저 기록을 지우면 결과가 사라지기 때문이다. 형식 (내 판단): 분석용 CSV(문항 단위)와 복원용 JSON(전체). 가져오기도 함께 둔다.
- **CSV를 분석할 때는 `invalid=0`인 행만 세야 도구가 화면에 보여준 수치와 일치한다** (내 판단 — 연구 사용 요건). 화면이 가려져 무효 처리된 문항도 원자료로 CSV에 남고, 그 행에도 `outcome`이 적힌다. 무효 문항은 §5.7에 따라 모든 지표 계산에서 제외되므로, 걸러내지 않고 `outcome`을 세면 도구의 수치와 달라진다.
- **스마트폰 + 기기 내 저장의 구조적 제약:** 회차별 추이는 **같은 기기에서 반복 검사했을 때만** 쌓인다. 교사의 폰으로 여러 학생을 검사하는 운용이면 문제없지만, 학생 개인 폰을 쓰면 추이가 흩어진다. 따라서 ① 설정 화면에서 "같은 기기로 반복 검사해야 추이가 쌓입니다"를 안내하고, ② 내보내기·가져오기를 눈에 띄는 위치에 두어 기기를 옮길 수 있게 한다 (내 판단).
- **측정 조건을 회차마다 함께 저장한다** (내 판단 — 연구 사용 요건). 기기 종류와 화면 크기, 브라우저와 버전, 화면 주사율 추정값, 입력 수단(터치/마우스), 그리고 **도구 자체의 버전 문자열.** 도구를 수정하면 버전이 올라가고, 분석할 때 어느 버전으로 측정한 자료인지 구분할 수 있어야 한다.
- 저장 공간이 꽉 차거나 localStorage를 쓸 수 없는 환경에서도 검사는 진행되고 결과 화면은 보여야 한다. 저장만 실패하고 그 사실을 교사에게 알린다 (내 판단).

**중단·이탈된 세션 (내 판단)**

- 회차마다 **완료 여부 플래그**를 둔다. 교사가 중단했거나 문항을 끝까지 못 간 세션은 미완료다.
- 미완료 세션도 **저장한다** — 참여도 자체가 정보다. 단 회차 목록에 "중단"으로 표시한다.
- **§5.7의 회차별 추이에는 완료 세션만 넣는다.** 중도 포기 세션이 들어가면 그래프가 아래로 꺾여 "나빠졌다"로 오독된다.
- 검사 중 화면이 가려지면(탭 전환, 전화, 화면 꺼짐) **즉시 일시정지**한다. 진행 중이던 문항은 무효 처리하고, 복귀 시 다음 문항부터 재개한다. 무효 문항 수를 결과에 기록하고 모든 지표 계산에서 제외한다(§5.7). 이 처리는 타이밍 엔진에 처음부터 들어가야 한다 — 나중에 끼워 넣을 수 없다.

**공용 PC 대응 (내 판단)**

학교 PC 한 대를 여러 학생이 돌아가며 쓴다. 현재 설계 그대로면 검사받으러 온 학생이 시작 화면에서 다른 학생들의 이름과 과거 결과를 볼 수 있다.

- 학생 식별은 **별칭을 권장**하고, 입력란에 그 안내를 둔다.
- 교사 영역(학생 목록, 결과, 내보내기)에 **4자리 PIN 잠금**을 선택 기능으로 둔다. 기본은 꺼짐 — 단독 사용 기기에서 매번 PIN을 요구하면 "최소한의 지원" 원칙에 어긋난다.
- PIN이 켜져 있으면 검사 종료 후 결과 화면으로 자동 전환하지 않고 잠금 화면을 거친다. 학생이 자기 결과를 보지 않게 하는 효과도 있다.

### 5.10 접근성과 독립 실행

- **학생 화면에 문장이 없다.** 그림, 아이콘, 소리, 움직임만.
- **세로 모드 스마트폰 기준으로 설계한다.** 가로로 돌려도 깨지지 않게 하되, 기준 레이아웃은 세로다.
- **반응 영역은 화면 하단 절반 전체** (내 판단). 스마트폰에서는 한 손으로 쥐고 엄지로 누르게 되므로, 하단 절반이 물리적으로 가장 닿기 쉽다. 작은 버튼을 겨냥하게 만들면 조준 시간이 반응시간에 섞인다.
- 자극 그림은 화면 상단 절반의 가운데에 크게 둔다. 수집 격자는 그 사이의 얇은 띠에 둔다 — 반응 영역을 침범하지 않는다.
- 결과 화면의 문항별 흐름 막대는 100문항이 좁은 화면에 들어가야 한다. **가로 스크롤되는 띠**로 만들고, 전체 모양을 축소해 보여주는 요약을 위에 둔다 (내 판단).
- 소리 켜기/끄기를 교사가 고른다. 소리에 과민한 학생이 있다 (내 판단).
- 애니메이션 줄이기 옵션 (내 판단: `prefers-reduced-motion` 존중 + 수동 토글).
- 검사 중 실수로 화면이 스크롤·확대·선택되지 않게 한다.
- 검사 중단 수단은 학생이 누를 수 없는 위치에 둔다 (내 판단: 길게 누르기 또는 화면 구석).
- 색만으로 정보를 구분하지 않는다 — 결과 화면의 막대는 색과 모양/위치를 함께 쓴다.

### 5.11 기술 스택

**웹 주소로 접속하는 정적 웹앱.** HTML + CSS + 바닐라 JavaScript, 빌드 도구 없음. (내 판단 — 사용자가 설계자에게 맡김)

웹 호스팅으로 확정됐으므로 `file://`의 제약(ES 모듈 차단, localStorage 불투명 출처 문제)이 없다. 모듈을 나눠 쓸 수 있고 localStorage도 정상 출처로 동작한다.

프레임워크를 쓰지 않는 이유: 유지보수 주체가 개발자가 아닐 가능성이 높고, 프레임워크 버전 관리가 이 프로젝트의 수명에 비해 부담이다. 서버 로직이 없어서 프레임워크가 해결해줄 문제도 없다.

**오프라인 동작은 서비스 워커로 처리한다** (내 판단). 한 번 접속하면 앱 전체가 캐시되어 인터넷이 끊겨도 검사가 가능하다. 홈 화면에 추가하면 앱처럼 열린다(PWA) — 스마트폰 중심 운용에서 교사가 주소를 매번 입력하지 않아도 된다.

측정 정확도 관련 결정:

- 자극 제시와 반응 기록은 `performance.now()` 기준으로 한다.
- 반응시간은 입력 이벤트의 `timeStamp`에서 자극 제시 시각을 뺀 값으로 한다 — 핸들러 실행 지연이 섞이지 않게 한다.
- 입력은 `pointerdown`으로 받는다 (`click`의 지연을 피한다). `touch-action`을 제어해 터치 지연과 스크롤을 막는다.
- 보상 애니메이션은 반응 기록 **이후**에 시작하고, 자극 제시 타이밍을 건드리지 않는다.
- 소리는 Web Audio API로 합성한다(음원 파일 없음). 브라우저 정책상 첫 탭 이후 활성화되므로, 시작 화면의 첫 입력에서 오디오를 깨운다.
- 화면은 전체화면을 권장하되 강제하지 않는다.
- **스마트폰의 터치 지연은 기기마다 다르다.** 연구용으로 쓰이므로, 이 값을 추정해 회차 메타데이터에 남긴다(§5.9). 절대 반응시간을 기기 간에 직접 비교하지 않도록 결과 화면에도 한 줄로 밝힌다. **같은 학생이 같은 기기에서 반복 측정한 회차 간 비교**가 이 도구가 보장하는 범위다.
- 화면 주사율(60Hz / 120Hz)에 따라 자극 제시 시각이 최대 한 프레임 흔들린다. 자극이 실제로 그려진 시각을 기준으로 반응시간을 계산한다.

## 6. 빌더에게 남긴 것

- 코드 구조, 모듈 분리, 파일 배치
- 테스트 전략. 최소한 다음 다섯 가지는 테스트로 고정한다:
  1. 문항 순서 생성 규칙 (§5.1 — No-Go 비인접, 간격 1~4 무작위, 평균 비율, 첫 3문항 Go)
  2. 지표 계산 (§5.7의 정의 테이블과 중복 계상 규칙)
  3. 배지 판정 (§5.8의 모든 조건, 특히 "3단계에서 잘 참은 학생"이 양호로 나오는지)
  4. 난이도별 문항 수 테이블과 No-Go 개수 (§5.6)
  5. 연습 결과 → 난이도 추천 매핑 (§5.3)
- 구체적 색상, 타이포그래피, 간격 — §5.10의 접근성 조건과 §2의 안티목표를 지키는 범위에서
- 소리의 실제 음색과 길이
- 애니메이션의 정확한 타이밍과 이징 — §5.4의 "짧고 작게" 범위에서
- 각 테마의 구체적 SVG/이모지 선택 — §5.5의 변별 조건을 지키는 범위에서
- 설정 화면과 결과 목록의 구체적 레이아웃
- 결과 화면의 반응형 처리 방식

## 7. 구현과 병행해야 할 일

연구·논문 산출물로도 쓰이기 때문에, 코드만으로 끝나지 않는 항목이 두 개 있다.

1. **§5.8 판정 기준값의 문헌 근거 조사.** 조급 반응 200ms, 조급 반응 20%, 누락 40%, No-Go 최소 8문항 — 모두 임시값이다. 고/노고 과제 문헌에서 통용되는 값을 확인해 조정한다. 구현은 이 값들을 한 곳의 설정 상수로 모아두는 것으로 선행할 수 있고, 조사 결과는 상수만 바꿔 반영한다.
2. **§5.7 "해석 한 줄" 문장 세트의 작업치료 전문가 검토.** 설계자가 초안을 쓰고, 검토 후 확정한다.

파일럿으로 확인해야 할 값: §5.6의 난이도별 평균 반응시간 가정(1.5 / 1.2 / 1.0초)과 그로부터 나온 문항 수 테이블, §5.3의 난이도 추천 규칙.

**실기기에서 반드시 확인해야 할 것 (구현 중 확인 불가):**

1. **터치로 소리가 실제로 나는지.** 브라우저는 사용자 제스처 안에서만 오디오를 허용하는데, 터치의 활성화 시점이 기기·OS 버전마다 다르다. 구현은 `pointerdown`과 `pointerup` 양쪽에서 해제를 시도하지만, 구형 iOS는 활성화 제스처 **안에서** 실제로 무음을 재생해야 풀린다. 소리는 글을 못 읽는 학생에게 규칙을 전달하는 수단이므로, 쓸 기기에서 한 번은 확인해야 한다.
2. **화면 하단 절반이 브라우저 도구 모음에 가리지 않는지.** `dvh`를 모르는 구형 iOS에서는 `100vh`가 도구 모음을 숨긴 높이라서, 반응 영역의 아래쪽이 도구 모음에 덮일 수 있다. 영역 자체는 존재하지만 눌리는 면적이 절반보다 작아진다.

**파일럿으로만 확인할 수 있는 것 하나 더:** §5.5의 테마 6종에서 **3단계 변별 난이도가 서로 동등한지**. 이모지 쌍의 지각 난이도는 추론으로 맞출 수 없다. 설계 기준은 동물 테마의 강아지/고양이이고, 나머지 테마를 그 수준에 맞추려 했지만 실제로 같은지는 학생이 해 봐야 안다. 테마별로 억제 실패율이 체계적으로 다르게 나오면 그 테마의 3단계 그림 쌍을 조정한다. 확인 전까지 **다른 테마로 측정한 회차의 수치를 직접 비교하지 않는다** — 같은 학생이 같은 테마로 반복한 회차 간 비교가 보장 범위다.
